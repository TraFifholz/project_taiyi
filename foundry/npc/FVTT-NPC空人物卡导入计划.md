# 个人服务器 FVTT：NPC 空人物卡导入计划

> 日期：2026-09-02。状态：计划内首批导入与验收完成；93 人已落库，补查 1 人复用、5 人明确暂缓。
>
> 目标：梳理已有 NPC，在个人服务器的《龙散战记》世界中建立或补齐头像、Token 和人物关系；战斗数据以后再填。本文件为本地 GM 工作资料，不发布到玩家 Wiki。
>
> 最初计划阶段仅核对本地资料。用户随后要求按 Goal 执行，已核实服务器、整理清单并上传图片；当前执行证据与续执行步骤见 [导入进度报告](imports/import-report.md)。下方第 2 节保留计划阶段基线，服务器现状以进度报告为准。

## 1. 范围与完成形态

- 以当前立绘总控中的 **93 个活跃身份**作为首批主名单，沿用 `LS-NPC-*` 稳定 ID，不重新编号。另设总控外补查池，避免把“有正式立绘”误当成“全体已有 NPC”。
- 每个身份最终对应一个确定的世界 Actor：已有卡补齐外观和关系，缺少卡才新建。**93 个身份不等于新建 93 张卡**，新增数量要在服务器去重后确定。
- 新建卡只填写名称、头像、原型 Token、简短身份与关系。属性、技能、专长、负赘、装备、奇能、战斗资源均不编制；系统必填的初始值保留并标注“数值待填”。
- 已有卡的数值、物品、效果、商店库存、权限和现有场景 Token 保留；不把已有完整卡清成空卡。
- 未登场、已故、失踪及幕后人物可以有 GM 档案卡。建立档案不代表登场、复活或公开秘密。
- 先交付世界 Actor 和原型 Token；不把所有人物摆进当前游戏场景，不制作完整怪物数据或商人库存。

## 4. 头像、Token 与空卡约定

| 内容 | 默认方案 |
|---|---|
| 正式图片来源 | `portrait-master.json` 的 `approvedAsset`＋`approvedSha256`，保留原图不覆盖 |
| 角色卡头像 | 从正式母版制作 512×512 头肩头像，保证脸、发型和重要身份特征可辨 |
| 原型 Token | 默认复用同一方形头像；适配目标世界现有圆框／动态环。需要单独构图时另存 Token，避免双重边框 |
| 完整立绘 | 作为可选展示资源保留；是否接入现有模块由服务器实际功能决定，不以新装模块为前提 |
| 派生清单 | 每人记录源图哈希、裁切框、尺寸、派生文件哈希及 FVTT 相对路径；按稳定 ID 命名，不把秘密身份放进文件名 |
| 新卡类型 | 目标 SWADE 实例支持的 NPC Actor 类型，执行时用实际数据模型验证 |
| 新卡原型 | 普通人形先用 1×1 格；唯一人物默认链接到 Actor。视野、光源与显示设置沿用世界适合普通 NPC 的基础模板，不赋予能力 |
| 卡面文字 | 一句话身份、当前叙事状态、已确认关系及“数值待填”。详细能力与长篇设定暂不灌入 |
| 存放位置 | 新卡放到“龙散 NPC”根目录下，按公开组织／用途浅层分组；幕后与已故人物单独归档 |
| 权限 | 新卡默认 GM 可管理、普通用户无权限；已有卡权限保留。待审关系不混入玩家拥有的 Actor |

若关系模块直接读取目标 Actor 名称，单改 Token 名不足以隐藏本名。未揭露人物的 Actor 显示名也使用已知代称；本名、真实阵营、未揭露关系保存在独立的 GM 专用档案中。不能依赖“折叠文字”或前端隐藏作为保密措施。

现成头像／Token 经核实符合当前身份且已采用时可直接复用。没有可靠图片的补查人物允许先有明确标注的占位图，但必须进入缺口表，不能计作“头像与 Token 完成”。

## 5. 人物关系如何整理和导入

关系范围包含 **NPC—NPC、PC—NPC、NPC—组织**。组织归属只代表归属，不推导“同组织所有人互相认识”。PC 使用服务器已有 Actor，不为建立关系复制 PC。

### 三类证据，分别落地

| 类别 | 判定 | 去向 |
|---|---|---|
| 已实跑／已公开 | 有逐字稿、战役记录或经核对的公开设定支撑 | 导入相应人物关系档案；PC 侧只放该 PC 已知的内容 |
| 已采用但未揭露的 GM 设定 | 有当前人物稿依据，明确尚未在场上公开 | 保存在 GM 专用关系档案；验证模块权限后才能导入相应私密入口 |
| 建议／推断／争议 | 仅来自评审或“关系建议”，或与实跑冲突 | 留在待定清单，不自动变成正式关系边 |

每条关系最少记录：稳定关系 ID、源人物 ID、目标人物／组织 ID、双方称谓、方向、简短说明、证据文件与定位、证据类别、谁已知、是否导入、服务器关系 ID。关系事实、证据类别和可见范围分别保存。

对称关系可在双方显示，但不能自动复制秘密说明；父女、上下级、师徒需分别使用对应称谓。喜欢／敌视等单方态度不推断成双向。**不编亲密度、羁绊等级、好感经验、奖励、触发宏或送礼偏好**；模块强制的默认值记作未评定，不当作剧情数值。

### FVTT 对接方案

本地 Stylish Relationship Tracker 源码使用 Actor 上的 `flags["stylish-relationship-tracker"].relationshipData`，人物关系通过 `entryType: "actor"` 与 `targetUuid` 关联，组织有独立的 `entryType: "organization"`。本地 GM 选择器支持所有世界 Actor，NPC 关系档案可作为验证对象。

执行时先核对服务器实际版本、接口、依赖、关系容量和权限，再通过该版本的正规保存接口追加或更新。不要直接拿另一世界的整个 flags 覆盖过来，也不默认启用关系双向同步。

若服务器未启用该模块或不能可靠隔离秘密：先把关系写入 GM 专用 Journal，以 Actor UUID 链接人物；玩家已知内容另行整理。卡面有文字不等于关系模块已验收，报告应明确实际采用了哪个载体。
